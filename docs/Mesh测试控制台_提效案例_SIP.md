## 标题

Mesh 固件测试提效：把人工设备操作验证沉淀成 79 步自动化测试项，单轮人力投入从 1 小时降到分钟级

---

## 提议背景

Mesh 固件的验证原来是**纯人工测试模式**：人在设备上按键、翻菜单，逐项验证固件行为（读配置、改角色、等设备重启、读回校验、再确认空口行为是否符合预期），再用文档和截图手工记录结果。这些操作本身不难，但**重复、碎片、等待长**，长期存在四个问题：

1. **重复劳动多**：同一批验证项每个固件版本都要重做一遍；串口和蓝牙两种连接方式各做一遍；不同设备角色再各做一遍。
2. **等待时间被浪费**：改配置后要等设备重启，位置/中继类验证要等广播周期（部分角色默认 3600 秒深睡），等待期间人只能干等。
3. **证据不可追溯**：读回值、监听结果靠截图和手抄，事后无法回答「当时到底是读到什么、有没有真的被中继」。
4. **覆盖靠经验、上手成本高**：验证项散在个人手里，换人就要重新对齐；参数与前后置条件多，新人做错也看不出错在哪一步。

**要做的事**：把人工步骤沉淀成机器可执行的测试项，做成一个本地可视化测试平台 —— 测试项以数据描述、执行过程自动留证、失败原因写成人话。**CLI 是平台的一项执行能力（自动化入口），不是原来的测试流程**：使用平台的人不需要记 CLI 参数，只需勾选测试项、看结论。目标不是"多跑几条命令"，而是**让每一轮验证都有可信、可追溯、可复现的结论，并让验证项成为团队资产**。

## 亮点

**1. 测试项即数据，扩展零代码**
9 条测试项 / 79 个步骤全部写在 `cases_l2_demo.json` 里。新增一条测试项 = 复制步骤结构 + 填命令与判据，不碰 Python 和前端代码。测试项与执行引擎解耦，谁写测试项谁就能维护；团队的测试点、缺陷复现步骤、外场问题都能按这个格式持续沉淀，**越补越厚而平台不改**。

**2. 证据闭环，拒绝"假通过"**
默认只做 dry-run；真实执行与"允许改配置/发消息"是两道独立开关。写配置**先读后写**、写后等待再读回对比；每一步都有中文判据，失败步骤直接写明原因与处理建议。命令执行成功不等于用例通过 —— 读回值不符、监听窗口里没看到预期副本都判失败；而像深睡角色的位置包这类无法稳定观测的内容，降级为**证据记录**，不参与判定。报告以 JSON 落盘，含每步命令、stdout/stderr、监听副本统计，可随时回溯。

**3. 串口与蓝牙两条通道都是一等能力**
串口侧覆盖**批量配置设备**（一次勾选多项配置批量下发、写前先读、写后读回）、**一键建立联系人**（让两台设备互相认识，解决通信验证前置条件）、**串口日志实时查看**与**空口监听取证**（观察者抓直收副本、中继副本、`POSITION_APP`）；蓝牙侧单台设备就能完成设备自身配置验证 —— 例如一条测试项自动完成 7 个 `US/*` 时区别名的写入、重启读回与回滚，共 26 个步骤，并支持持续收发与页面内实时日志。哪条通道合适就用哪条，不必为了"能自动化"去接一堆线。

**4. 把失败变成可定位的结论**
控制台不只是"跑通/跑不通"，它把现象归因到具体行为：例如角色用例失败时能指出「TRACKER 发完位置后会按 `position_broadcast_secs`（固件默认 3600 秒）深睡，睡眠期间 USB-CDC 与射频一起断电，串口会从系统里消失」，并给出「唤醒设备后重跑 / 确认端口号是否变化」的处理建议；同时纠正了一处**用例设计缺陷**（原先断言"写入 60 秒再读回 60 秒"，实际固件回落默认值 3600，属于把错误预期当判据），避免后续继续产出无意义的失败单。

**5. 零依赖、一键启动、团队可复制**
后端只用 Python 标准库，前端是原生 HTML/CSS/JS，无构建步骤、不占服务器：`.\start_dashboard.ps1` 一条命令起服务，浏览器打开 `127.0.0.1:8765` 即用。报告目录可用环境变量指向共享路径，多人跑的结果能汇总到一处。

## 解决方案

**整体架构（四层，职责分明）**

```text
浏览器本地页面（用例勾选 / 设备连接 / 执行结果 / 报告）
        │ JSON API
server.py（本地 http.server，127.0.0.1:8765，提供 API + 静态文件）
        │ 子进程
runner.py（用例执行引擎：读语料、跑步骤、判期望、出报告）
        │
safe_meshtastic_cli.py（CLI 包装：关闭 DTR 复位）→ meshtastic.exe（官方 CLI，串口 / --ble）
```

**关键设计**

1. **用例模型**：每一步声明「目标设备 / 依赖（单机、双机、观察者）/ 是否写操作 / 期望输出 / 读回字段 / 等待与重试 / 监听窗口」。依赖不满足时步骤自动裁剪并在报告里标记，因此同一条用例在不同设备数量下都能安全执行。
2. **执行保护**：dry-run 默认 + 写操作二次确认 + 先读后写（值一致直接跳过）+ 写后固定等待 + 超时/重试（重试只针对命令失败，绝不掩盖判据不符）。
3. **判据体系**：区分「命令是否成功」与「行为是否符合预期」；区分「断言」与「证据」。中继验证通过监听副本的 hop 递减判定，位置/遥测类内容作为证据留存而不是硬性通过条件。
4. **稳定性细节**：CLI 包装关闭 DTR 复位（避免每次开串口把设备打回 boot 造成随机失败）；protobuf 文本输出按行解析并固定 UTF-8；BLE 下设备重启掉线的失败原因在报告里保留原始错误。
5. **体验打磨**：串口/蓝牙两套布局、用例 hover 直接显示「需要几台设备」、蓝牙测试项可折叠、未勾选的字段统一置灰、卡片间距规整 —— 降低误操作与阅读成本。

**落地与复用**

- 使用流程：选测试系统 → 扫描串口 / 蓝牙 → 跑前置检查 → 勾选测试项 → 运行 → 看结果与报告。
- 复制到其它产品：换设备名 / 端口与语料即可，引擎与前端不需要改。
- 现状与规划：当前覆盖 **Meshtastic** 固件；**MeshCore 界面入口已预留，测试能力暂未支持，已纳入后续开发规划**。下一步补齐真机回归（蓝牙时区测试项、角色类测试项全流程）、把语料接入版本发布前的定时回归、把共享目录下的报告汇总成通过率与失败原因趋势。

**成效**

| 指标 | 之前（人工操作） | 现在（平台执行） |
| --- | --- | --- |
| 单轮人力投入 | 全程盯 ≥ 1 小时 | 点击 + 核对报告 ≈ 5 分钟 |
| 测试项规模 | 靠个人经验零散执行 | 9 条测试项 / 79 步 / 4 模块，可勾选、可全量 |
| 常用操作 | 逐台设备手工按键改配置、手工建联系人 | 批量配置下发、一键建立联系人、一键跑测试项 |
| 证据形态 | 截图 + 手抄，事后不可查 | 每步命令、输出、判据、监听统计的 JSON 报告 |
| 新增测试项成本 | 重新摸一遍操作步骤 | 写 JSON，10–20 分钟/条，零代码 |
| 失败定位 | "跑不通，再手工试" | 直接给出根因判断与处理建议 |
| 上手成本 | 需要熟悉设备菜单与参数 | 打开页面点两下即可上手 |

## 附：数据口径与来源（仅供核对，发布时不带）

- 用例规模：`tests/meshtastic_cli_demo/cases_l2_demo.json` 统计 = 9 条用例 / 79 个步骤 / 4 个模块（测试前检查 2、可选取证 2、设备角色验证 4、BLE 设备验证 1），其中 19 步为写操作、7 个监听/证据窗口、2 种连接方式。
- 蓝牙用例：`L2-BLE-TZ-CHECK` 26 步 = 1 步记录原时区 + 7×(写入 + 等待重启 + 读回) + 回滚与结果读回。
- 「≥ 1 小时」口径：79 步手工执行，按「写/读回 + 记录输出 ≈ 40 秒/步」估算 ≈ 53 分钟，再加角色用例的监听窗口与蓝牙用例的 7 次重启等待，保守取 ≥ 1 小时；**如团队有实测基线，请用你们的数字替换**。
- 「约 5 分钟」口径：勾选用例 + 点击 + 核对报告与失败原因的人工时间；设备等待（重启、广播周期）不占用人力。
- TRACKER 深睡结论来源：固件 `PositionModule.cpp` 中 `doDeepSleep(position_broadcast_secs)` 与「Sending position and sleeping for %us interval in a moment」日志；默认值来自 `Default.h` 的 `default_broadcast_interval_secs = 3600`。
- `2147483647` 结论来源：`Default.h` 中 `#define MAX_INTERVAL INT32_MAX`（注释说明为避免 Apple 客户端溢出），语义为「不做周期性上报」。
