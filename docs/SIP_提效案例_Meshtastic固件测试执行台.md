# SIP 提效案例：Meshtastic 固件测试执行台

## 标题

将 Meshtastic 固件高频回归从手机 App 手工操作沉淀为一键执行与自动留证

## 提议背景

在以往固件测试中，测试人员经常需要打开手机 App 连接设备，再逐台修改 Region、Modem Preset、频率覆盖、频道等配置；两台设备互相识别时还要拿手机分别扫描对方二维码。测试项执行、结果记录和失败定位也主要依赖人工操作、截图和经验判断，重复轮次多且复核成本高。

Meshtastic 固件测试执行台将这些高频、可判定的操作收敛到本地可视化页面：串口可一键配置并支持多设备批量下发，可一键建立联系人；测试项可一键运行、自动判定并生成报告。BLE 则面向真实用户链路，模拟“连接设备—读取/修改配置—发送/接收消息—保持连接”的使用过程。人工继续负责初次体验、App 交互与异常复核，平台承担重复回归。

## 使用频率

- 每个候选固件版本进入回归时执行。
- 缺陷修复、配置变更或通信问题复现后执行对应测试项。
- 初次测试仍保留人工 App 连接、配对、交互和体验验证；稳定且重复的检查逐步沉淀为自动化测试项。

## 亮点（200 字内）

平台将高频固件回归集中为可执行能力：串口支持一键/多设备配置、自动建立联系人和测试项批量运行；BLE 面向真实用户场景，覆盖单设备连接、配置检查、持续收发与长连接稳定性。每项操作保留读回、判据和报告，避免“命令成功即通过”。人工聚焦首次体验与异常复核，重复回归交给平台；测试项可持续补充，覆盖范围随项目积累扩大。

# 一、解决方案

## 1. 平台定位与整体流程

平台定位为 **Meshtastic 固件测试执行台**，服务于 Meshtastic 固件设备的版本回归、配置验证和问题复现。当前 Wio Tracker L2 用于试点验证，不是平台的设备边界；MeshCore 仅保留后续规划入口，不作为当前已支持能力。

平台不是要替代所有人工测试，而是将可重复、可判定的动作沉淀为执行流程：

```text
人工初次体验 / App 交互验证
            │
            ├── 将稳定、重复的检查沉淀为测试项
            ▼
测试台选择设备和测试项 → 自动执行 → 读回 / 接收证据判定 → JSON 报告
            │                                                    │
            └─────────────── 异常复核与新用例补充 ──────────────┘
```

## 2. 三个界面与对应能力

### 2.1 测试执行界面：把手工步骤变成一键操作

测试执行界面是日常使用入口，包含串口/BLE 连接、设备当前配置、测试项、配置写入和通信验证。

- **一键配置与批量配置**：通过串口读取设备现值；仅当当前值与目标不一致时才下发，再等待设备恢复并读回确认。适用于 Region、Modem Preset、Frequency Override、频道、角色、Wi-Fi、GPS、蓝牙等配置项。
- **一键建立联系人**：替代手机 App 双向扫码的重复操作。平台导出两台设备的联系人信息并互相导入，再以 NodeDB 和后续通信结果验证是否生效。
- **一键运行测试项**：按模块或单条执行测试前检查、角色行为、串口通信回归和 BLE 单设备验证。测试项以 JSON 描述，可继续补充，不需要重写页面框架。
- **通信前置控制**：US / EU_868 公共频道回归会先读取两端通信配置；Region 不符时只自动修正 Region 并读回。Modem Preset、Frequency Override 与频道 PSK 仍作为独立前置条件，避免为得到 PASS 而覆盖问题。

### 2.2 报告界面：结果自动判定、证据自动归档

每次运行都会生成结构化 JSON 报告，并在报告界面保留可查看和下载的记录。报告中包含测试项、执行步骤、使用的命令、读回值、输出、判定条件、PASS/FAIL/SKIPPED 状态和失败原因。

判定遵循“可验证证据优先”原则：配置写入不能只看命令返回，必须读回；通信不能只看发送命令退出，必须保留接收、ACK 或设备可见证据。这样可减少人工整理测试记录的时间，也便于固件问题复现、版本对比和缺陷沟通。

### 2.3 日志界面：实时监听串口原始日志

日志界面用于在本机实时监听指定串口的设备原始输出。测试人员选择日志串口和波特率后，可扫描串口、开始监听或停止监听；监听页面持续显示设备运行日志，同时将日志文件落盘到本地项目目录。

该界面适合辅助定位重启、深睡、异常输出、无线收发过程和偶现问题。它不直接替代测试项的 PASS/FAIL 判定，而是为失败复核、缺陷复现和固件研发沟通提供可追溯的原始证据。

## 3. 技术实现与质量控制

### 3.1 分层实现

| 层级 | 实现内容 | 作用 |
| --- | --- | --- |
| 页面层 | 原生 JavaScript 测试台页面 | 选择连接方式、设备、配置和测试项；展示进度、结果与报告 |
| 执行层 | Python 执行器 | 将测试项拆为读取、条件写入、等待、读回、比较和通信步骤 |
| 设备交互层 | Meshtastic 官方 Python CLI/API、Web Bluetooth GATT | 保持与官方 Meshtastic 生态一致，不自行实现 Mesh 协议 |
| 证据层 | 本地 JSON 报告与运行进度记录 | 记录步骤、输出、判据和失败原因，支持复核与复现 |

### 3.2 关键机制

1. **先读后写**：读取当前值；一致则跳过写入，减少设备重启和无意义操作。
2. **写后读回**：涉及配置的操作必须等待设备恢复后读回，不能只以 CLI 输出“已写入”判定通过。
3. **受控自动修正**：回归用例只修正其明确声明的配置项。例如区域回归只修正 Region，不覆盖 Frequency Override、Modem Preset 或 PSK。
4. **结构化判定**：用例可以定义预期值、接收证据、比较规则、超时和失败提示；失败会保留问题步骤，不通过放宽阈值制造 PASS。
5. **敏感信息处理**：报告对 PSK、密码、密钥等字段进行脱敏；发布截图前仍需人工复核。

## 4. 适用范围与边界

| 场景 | 平台适用方式 | 当前边界 |
| --- | --- | --- |
| 固件版本回归 | 执行稳定、可重复的配置和通信测试项 | 初次体验测试仍需人工完成 |
| 配置验证 | 串口/BLE 读取、必要时写入、等待、读回 | 不支持的 CLI/固件字段应如实标记为人工项 |
| 多设备准备 | 串口批量配置、联系人互识、通信前置检查 | 不以自动改写 PSK 等方式掩盖配置问题 |
| BLE 用户链路 | 单设备连接、配置检查、持续收发、长连接稳定性 | 不承诺双设备同类 BLE 并发通信 |
| 日志与问题复现 | 串口日志、结构化报告、失败步骤定位 | 不替代射频、天线、功耗、结构等硬件专项测试 |

## 5. 可持续扩展的方向

- 将新的固件缺陷复现步骤和人工测试经验沉淀为 JSON 测试项。
- 为更多 Meshtastic 设备补充默认配置、设备识别和产品专属用例。
- 将本地报告汇总到共享目录，形成版本通过率、失败原因分布和趋势对比。
- 在真实回归流程稳定后，接入版本发布前触发或定时运行机制。
- 未来为 MeshCore 建立独立的协议、配置映射和测试项，不与 Meshtastic 路径混用。

### 6.3 本地使用与访问限制

完整的本地部署指南、操作方法和测试项说明均已收录在项目 GitHub 仓库：[Weiii1222/Meshtastic-test-platform](https://github.com/Weiii1222/Meshtastic-test-platform)。其他同事在仓库同步当前源码后，可按仓库说明在本地搭建并运行平台。

当前 SIP 链接可打开站点入口，但当前环境未获得可读取案例或编辑页面的权限，不能据此断言其他同事一定无法访问。发布前建议由 SIP 管理员确认公司账号的查看、创建和发布权限，链接中的 `code` 是否为临时邀请码，以及发布后的可见范围。

若暂时无法处理权限，可在 SIP 页面或发布通知中标注：**“SIP 页面访问受公司账号与权限策略控制；项目代码与完整使用指引见 GitHub 仓库，SIP 发布权限待管理员开通。”**

### 6.4 迭代状态与风险提示

平台仍处于迭代优化阶段，尚未完全成熟，可能存在尚未发现的使用问题与 bug。当前适合作为可重复回归、配置检查、日志取证和问题复现的辅助执行台；涉及首次用户体验、手机 App 交互、复杂现场环境和异常结论时，仍应由测试人员进行人工复核，并将问题持续沉淀为后续测试项和修复任务。
