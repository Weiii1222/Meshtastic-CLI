## 摘要（300 字内）

原来 Mesh 固件的验证是**纯人工测试模式**：人在设备上按键、翻菜单逐项验证，再用文档和截图手工记录。我用 AI 编码 Agent 把这套流程做成了一个本地自动化测试平台「Mesh 固件测试控制台」：测试项以数据描述（当前 9 条 / 79 步 / 4 个模块，覆盖串口与蓝牙两种连接），一键执行并自动生成带证据的 JSON 报告。**平台基于官方 Meshtastic 生态开发**：设备交互全部通过官方 meshtastic Python CLI（`meshtastic` 2.7.11）执行，配置字段与枚举对照官方 protobufs，固件行为结论对照官方固件源码，平台不自己实现 Mesh 协议。

过程中 AI 承担方案拆解、代码实现（约 1.3 万行）、自动化回归脚本编写（31 个）与文档起草；我负责定判据、做取舍、真机复核。**单轮验证的人力投入从 ≥ 1 小时降到约 5 分钟**，新增测试项 10–20 分钟一条且零代码。全程遵循「人来定判据、AI 来干活、证据可复核」的原则，不接受任何无法追溯的结论。

## 一、案例一句话

测试岗位独立发起，**基于官方 Meshtastic Python CLI 与官方 protobufs / 固件源码**，用 AI 编码 Agent 交付了一个可复用的固件自动化测试平台，把重复的人工验证工作转成了可追溯、可扩展的团队资产。

## 二、为什么提这个案例（提案背景）

1. **公司推动 AI 提效，需要一个非研发岗位也能落地的真实样例**。本次由测试岗位发起并完成，全流程使用 AI 编码 Agent，不依赖额外研发资源。
2. **原有流程纯人工，痛点明确**：同一批验证项每个固件版本重做一遍；改配置要等设备重启、等广播周期，人只能干等；证据靠截图手抄，事后无法回答"当时读到的值是多少"；验证项散在个人手里，换人就要重新对齐。
3. **AI 恰好补在这三个位置**：把经验型操作翻译成可判定的测试项、把重复编码工作接过去、把每次改动都自动回归一遍。人从"操作员"变成"判据定义者与验收者"。

## 三、技术基础：基于官方 Meshtastic 生态开发（不自研协议）

平台的定位是"测试平台"，不是"另一个 CLI"。所有设备交互都交给官方组件，我们只做组织与判据：

| 官方组件 | 版本 / 来源 | 平台如何使用 |
| --- | --- | --- |
| **官方 Meshtastic Python CLI** | `meshtastic` **2.7.11**（官方 `meshtastic/python` 开源仓库） | 设备交互的**唯一执行入口**：串口与 `--ble` 两条通道都由官方 CLI 完成 |
| **官方 protobuf 定义** | 官方 `meshtastic/protobufs` 仓库 | 配置字段、角色 / 区域 / 时区枚举与判据语义的对照来源 |
| **官方固件源码** | 官方 `meshtastic/firmware` 仓库 | 固件行为结论的依据（默认值、深睡逻辑、周期上报等） |
| pyserial / Bleak | 官方 CLI 的依赖（3.5 / 3.0.2） | 串口枚举与 BLE 连接 |

唯一的一层本地包装 `safe_meshtastic_cli.py` 仍然调用**官方 CLI 入口**，只在进程内调整串口打开方式（避免 Windows USB-CDC 上读命令触发设备复位）与可选的 BLE 配对参数——**不改协议行为、不改动官方包**。

**为什么强调这一点**：① 可信 —— 协议交互不依赖自研实现，出问题能回到官方行为对照；② 可跟随升级 —— 官方 CLI 升级即可同步设备支持；③ 可复用 —— 换成其它 Meshtastic 设备同样适用。

## 四、AI 是怎么用的（应用方式）

| 环节 | AI 承担 | 人承担 |
| --- | --- | --- |
| 方案与测试项设计 | 阅读官方固件源码与协议定义，把角色行为翻译成可判定的测试项与判据 | 确认「这条判据是否真的能证明行为正确」 |
| 代码实现 | 执行引擎、本地服务、前端页面与样式（约 1.3 万行） | 架构取舍、功能验收、真机联调 |
| 自动化验证 | 编写 31 个浏览器回归脚本，改动后自动复跑并截图取证 | 判断回归结果是否可信、是否覆盖了该覆盖的路径 |
| 问题定位 | 从日志与现象反推固件行为（例如深睡导致串口消失、哨兵值语义） | 确认结论、决定是否修订测试项 |
| 文档产出 | 起草 README、测试项说明、提效案例、覆盖矩阵 | 修订表述、核对数据口径 |

## 六、AI 应用的边界与规范（我认为最重要的部分）

1. **判据不能由 AI 说了算**。AI 写代码快，但"什么才算通过"必须由人定义：每条测试项都要能回答"这条判据为什么足以证明行为正确"，证明不了的就降级为证据记录。
2. **不接受假通过**。命令执行成功不等于测试项通过；AI 给出的结论必须能被报告里的原始输出复核，读回值不符就判失败。
3. **真机结论必须真机复核**。AI 无法替代硬件验证，涉及射频、功耗、实际空口行为的部分只做证据留存与人工确认。
4. **过程可回溯**。所有改动进 Git，一次提交只做一件事；AI 生成的文档与结论需人工修订后再对外。
5. **敏感信息不外发**。报告包含设备公私钥相关字段，外发前统一脱敏。

## 七、可复制性与推广建议

- **适用场景**：重复性高、步骤相对固定、对证据可追溯有要求的测试 / 运维 / 数据处理工作。
- **复制成本低**：本平台更换产品只需改设备配置与测试项语料；其它团队照「用例即数据 + 自动留证 + AI 自测回归 + 人定判据」这套方法即可上手。
- **建议动作**：把本案例作为内部 AI 应用样例分享；沉淀一份简短的《AI 协作规范》——人来定判据、AI 来干活、证据可复核、结论可追溯。
